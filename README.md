# muscle-log

筋トレの記録アプリ。**iOS / Android 両対応、オフラインで完結**（サーバー・アカウント登録なし）。

個人開発。企画・設計・実装・デバッグを一人で担当。

## 概要

muscle-log は、日々のトレーニング内容（種目・重量・レップ数）を記録するスマホアプリ。サーバーを持たず、記録はすべて端末内の SQLite に保存されるため、通信環境のないジムの地下でも問題なく使える。

設計の軸は「**前回の記録を起点に、今日の分だけ調整する**」こと。前回のメニューをワンタップで複製し、種目ごとに前回の重量・レップ数を見ながら入力し、過去の傾向から次にやる種目まで提案する。ゼロから毎回入力し直す手間をできる限り減らすことを目指した。

---

## 解決した課題

既存の筋トレ記録アプリの多くは「毎回すべて手で入力する」ことを前提に作られている。しかし実際のトレーニングは、同じ種目・似た重量とレップ数を毎回繰り返すことがほとんどで、そこに入力の手間がかかるほど記録が続かなくなる。

muscle-log では、この「**記録の摩擦**」を減らすことを最優先の課題として設計した。

- 前回と同じ内容なら、選んで複製するだけで済むようにする（[前回コピー](#工夫した点)）
- 種目を選ぶ判断すら、過去の傾向から提案できるようにする（[次の種目の提案](#工夫した点)）
- 重量を思い出す・前回の記録を見るためにアプリを行き来する手間をなくす（前回の重量・レップ数の自動表示）

「入力を減らす」ことそのものをアプリの中心機能として据えている点が、一般的な記録アプリとの違い。

## 主な機能

### 1. トレーニング記録
種目を複数追加し、それぞれにセット（重量・レップ数）を複数記録する。種目ごとにメモ（フォームの気づきなど）も残せる。日付はワンタップ操作かカレンダーから選択。記録の作成・編集・削除に対応。

### 2. 履歴の一覧・詳細
日付順の一覧から、各記録の種目・セット内容を確認できる。

### 3. 前回コピー — アプリの核となる機能
履歴の中から任意の記録を選び、「この内容をコピーして今日の記録にする」を押すだけで、種目構成とセット構成を引き継いだ新しい記録の入力画面が開く。日付は今日に、内容はその場で自由に編集可能。保存すると独立した新しい記録として残り、元の記録は変更されない。

### 4. 次の種目の提案
種目を入力すると、過去の履歴から「その種目の直後によく記録されている種目」を集計し、候補として提示する（例: いつもベンチプレスの次にインクラインプレスをしていれば、ベンチプレスの後にインクラインプレスが候補に出る）。タップ一つで種目を追加できる。履歴が少なければ無理に提案せず、汎用の「よく使う種目」候補にフォールバックする。

### 5. 前回の重量・レップ数の参照
種目名を入力すると、その種目を最後に記録したときの重量・レップ数を自動で表示し、ワンタップでそのままセットにコピーできる。

## 使用技術

| 領域 | 技術 | 採用理由 |
|---|---|---|
| 言語 | TypeScript | 型による静的検査で、DB スキーマからフォームの状態管理までの整合性を保証する |
| フレームワーク | React Native + Expo (SDK 54) | 単一コードベースで iOS / Android 両対応。Expo Go により実機での動作確認サイクルを短縮できる |
| ルーティング | Expo Router | ファイルベースルーティング。画面構成がディレクトリ構造にそのまま現れる |
| データベース | SQLite (`expo-sqlite`) | 端末内完結・オフライン動作の要。通信不可の環境（ジム地下など）でも動く設計 |
| ORM / マイグレーション | Drizzle ORM (`drizzle-orm` / `drizzle-kit`) | スキーマ定義から型と SQL マイグレーションの両方を生成。生 SQL を書かずに自己結合クエリまで型安全に書ける |
| 日付選択 | `@react-native-community/datetimepicker` | 各 OS のネイティブカレンダー UI をそのまま利用 |

サーバーを持たない構成にしたのは意図的な選択で、個人の記録アプリにアカウント基盤やバックエンド運用コストは不要と判断したため。将来的にクラウド同期が必要になっても、ローカル DB を正として上に同期層を足す形で拡張できる。

## 使い方

### 必要なもの
- Node.js
- スマートフォン（[Expo Go](https://expo.dev/go) アプリをインストール）または Android エミュレータ

### セットアップと起動

```bash
npm install
npm start
```

ターミナルに表示される QR コードを、iPhone は標準カメラアプリで、Android は Expo Go アプリで読み取るとアプリが起動する。

### その他のコマンド

| コマンド | 内容 |
|---|---|
| `npm run typecheck` | TypeScript の型チェック |
| `npm run android` | Android エミュレータで起動 |
| `npx drizzle-kit generate` | `src/db/schema.ts` の変更から SQL マイグレーションを生成 |

## アーキテクチャ

```
app/                         画面（Expo Router のファイルベースルーティング）
├── _layout.tsx               共通ナビゲーション + 起動時マイグレーション制御
├── index.tsx                 ホーム（履歴一覧）
└── workout/
    ├── new.tsx                記録の新規作成（コピー機能もここに統合）
    ├── [id].tsx                記録の詳細
    └── [id]/edit.tsx           記録の編集

src/
├── db/
│   ├── schema.ts              テーブル定義（Drizzle）
│   ├── client.ts               SQLite 接続
│   └── queries.ts             ★ データアクセス層。画面は SQL を直接書かず、ここだけを経由する
├── components/
│   ├── WorkoutForm.tsx         記録の作成・編集・複製で共有する入力フォーム
│   └── CenteredMessage.tsx     ローディング / 空状態の共通表示
├── utils/date.ts               日付フォーマット・演算の共通処理
└── theme/colors.ts             配色の一元管理

drizzle/                       自動生成される SQL マイグレーション
```

**画面は DB を直接触らない。** すべての読み書きは `src/db/queries.ts` の関数を経由する。これにより、画面側のロジックとデータアクセスの実装が分離され、クエリの最適化やスキーマ変更の影響範囲を `queries.ts` 一箇所に閉じ込められる。

### データモデル

```
workout        1回のトレーニング（日付のみ）
  └─ exercise_entry   その日の種目（種目名・表示順・メモ）
       └─ set_entry        1セットごとの記録（重量・レップ数）
```

セットを独立した行として持つことで、「3セット目だけ重量を落とした」のような実際のトレーニングの記録がそのまま表現でき、将来的な「種目別の最大重量の推移」のような集計にも対応できる。メモは種目単位で持たせている（1日の総評よりも「この種目でフォームを意識した」のような種目ごとの気づきの方が実用的なため）。

種目マスタは持たず、`exercise_entry.name` に種目名を文字列としてそのまま保存するシンプルな構成にした。次の種目の提案・前回値の参照はいずれもこの文字列の集計だけで実現でき、マスタ管理のコストをかける必要がなかった。

## 工夫した点

### 1. 「次の種目」提案は AI を使わず、SQL の自己結合だけで実装した

過去の全履歴から「同じワークアウト内で、ある種目の直後に来た種目」を数え上げ、多い順に提案する。実装は `exercise_entry` テーブルを表示順（`sort_order`）で自己結合する SQL 一発。

```sql
-- 概念的なイメージ
SELECT next.name, COUNT(*) AS count
FROM exercise_entry AS current
JOIN exercise_entry AS next
  ON current.workout_id = next.workout_id
 AND next.sort_order = current.sort_order + 1
WHERE current.name = ?
GROUP BY next.name
ORDER BY count DESC
```

機械学習モデルを持ち出すこともできたが、精度・実装コスト・説明可能性のバランスを考えると、このドメインでは単純な頻度集計で十分に実用的な提案ができると判断した。**履歴が少ない・初めての種目には無理に提案を出さず**、汎用の頻度ベース候補に自然にフォールバックする設計にしている。

### 2. 「入力の手間を減らす」を複数の機能で多層的に実現

「前回コピー」（記録単位の複製）と「前回の重量・レップ数の参照」（種目単位の参照＋部分コピー）は役割が異なる。前者は「今日もだいたい同じメニュー」というケースに、後者は「今日は種目を選び直すが、重量は前回を参考にしたい」というケースに対応する。両方を組み合わせることで、複製したメニューを個別に微調整する使い方も、その場で都度種目を選びながら前回値を参照する使い方も、同じ入力フォームの上で完結する。

種目名の入力中は、1文字ごとに DB へ問い合わせが飛ばないよう 400ms のデバウンスをかけ、さらに同じ種目名への問い合わせ結果はフォーム内でキャッシュして再利用している。

### 3. タイムゾーンに起因する日付バグの発見と修正

日付を1日進める／戻す操作で、進めても変化がない・戻すと2日戻るという不具合が発生した。原因は `Date#toISOString()` が常に UTC に変換すること。日本時間（UTC+9）ではローカルの日付操作後に UTC 変換で日にちがずれ、+1日の操作が実質 0 日に、-1日の操作が実質 -2日になっていた。`toISOString()` を使わず、`getFullYear()` / `getMonth()` / `getDate()` というローカルタイムの getter から直接日付文字列を組み立てる方式に修正し、日付操作全体をタイムゾーンに依存しない実装に統一した。

### 4. 実機テストで気づいた導線の不具合を修正

「前回コピーで複製 → 保存」のあと、`router.back()` で1つ前の画面に戻す実装にしていたところ、コピー元の（古い）記録の詳細画面に戻ってしまい、「保存されたのかどうか分かりにくい」という問題があった。`createWorkoutWithDetails` が返す新規レコードの ID を使って、保存後は**新しく作られた記録の詳細画面に直接遷移**するよう修正した。

### 5. 開発環境側の実務的な問題への対応

- **OneDrive 同期フォルダ内での開発**: `node_modules` の大量のファイル操作と OneDrive の同期が競合し、`npm install` が `EPERM` で失敗する問題が発生した。`node_modules` の実体だけを OneDrive 管理外のディレクトリに置き、プロジェクト内には NTFS のディレクトリジャンクションを張ることで、コマンドの使い勝手を変えずに解決した。
- **Expo Go の SDK バージョン不一致**: 実機の Expo Go アプリが対応する SDK と、プロジェクトの SDK が異なると実機で開けない。Expo が配布する SDK ごとの互換パッケージ一覧（`bundledNativeModules.json`）を直接参照して依存関係を1つずつ検証し、実機の Expo Go が対応するバージョンに正確に合わせた。
